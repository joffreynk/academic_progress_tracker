# Deployment

This project is prepared for a Cloudflare Wrangler deployment using a Cloudflare D1 SQLite database.

## Required setup

1. Install dependencies:
   - npm install
2. Create the D1 database:
   - npx wrangler d1 create student-academic-reporting-db
3. Update the `database_id` value in `wrangler.jsonc` to the created database ID.
4. Apply the schema to the D1 instance:
   - npx wrangler d1 migrations apply student-academic-reporting-db --local
   - npx wrangler d1 migrations apply student-academic-reporting-db --remote
5. Set the app runtime secret:
   - `SETUP_TOKEN` (the only runtime secret; there is no session secret to configure — sessions are random server-stored tokens)
6. Run the app locally with Wrangler when needed:
   - npm run wrangler:dev

## Environment variables

Use these values for your deployment environment:

- `SETUP_TOKEN` — one-time bootstrap token for the first admin setup
- `NODE_ENV=production`
- `NEXT_TELEMETRY_DISABLED=1`

`AUTH_SECRET` in `.env.example` is not read by the application and can be ignored or removed. For local development, `DATABASE_URL` can point to a SQLite file such as `./.data/local.db`.

## Wrangler configuration

The project includes a D1 binding in `wrangler.jsonc`:

- binding: `DB`
- database_name: `student-academic-reporting-db`

This matches the code in `src/db/index.ts`, which prefers the Wrangler D1 binding and falls back to a local SQLite file when not running in Cloudflare.

## Deployment flow

1. Update the D1 database ID in `wrangler.jsonc`.
2. Run `npm install`.
3. Run `npm run build` if needed for the deployment target you are using.
4. Run `npm run wrangler:deploy`.
5. Open the app and complete the first-time setup flow.

## Notes

- This project uses SQLite/D1, not PostgreSQL.
- Keep all secrets out of version control.
- The app is compatible with Wrangler D1 and local SQLite development.
- Migration `0003` (club tables `clubs`/`club_teachers`/`club_members`/`club_activities` plus the `teachers.department` column drop) is applied to the local SQLite database only. Apply it to the remote database with `npx wrangler d1 migrations apply student-academic-reporting-db --remote` **before** deploying the build that expects it, so code and schema move together.
- Migration `0004` (monthly record entry, §193: adds `monthly_entries` and `monthly_student_entries`) is applied to the local SQLite database only for the same reason — run the remote D1 apply before deploying the build that expects it.
- Migration `0005` (adds `club_activity_records`, the per-student club activity rows) is applied locally only — run the remote apply before deploying the clubs per-student records feature.
- Migration `0006` (the daily→monthly merge) renames `daily_lessons` → `monthly_lessons` and `daily_student_records` → `monthly_student_records`, renames the column `daily_lesson_id` → `monthly_lesson_id`, backfills `audit_logs.entity_type = 'daily_lesson'` to `monthly_lesson`, and drops `settings.reportingCadence`. Data is preserved by the rename. It is applied locally only — run the remote apply before deploying code that expects the new table names.
- Migration `0007` (adds `subject_students`, the teacher-managed subject rosters behind **Manage students** on the monthly form) is applied locally only — run the remote apply before deploying the subject-group feature.
- `.open-next/` is generated by `npm run build` and ignored by Git — rebuild immediately before `npm run wrangler:deploy`.
- All password entry points share one rule: at least 6 characters with an uppercase letter, a lowercase letter, a number and a symbol (setup, password change, admin/teacher create and reset, and generated passwords).
